# 用提示词驱动整个构建——这19集课程究竟是怎么写成的

**画面：** 不是代码——而是本仓库自己的 `git log --oneline`(75 次真实提交)，以及产出了其中绝大多数提交的那句两个词的指令：`Continue to Episode N.`

## 为什么需要这份文档

本课程的每一课，都是通过真实、可运行的代码来讲授架构、安全和验证方面的纪律的。但没有一课说过，那些代码究竟是谁敲出来的。这一份文档要说清楚这件事：`src/saas_copilot/` 里的每一行代码、每一个测试、以及另外18篇课程文档里的每一篇，都是由一个人通过自然语言指挥一个 AI 编程智能体(Claude Code)产出的——从来不是靠手工敲实现代码。这不是一句提一下就翻篇的免责声明。它值得单独作为一课来讲，因为*如何*在一次真实、跨越多个会话的构建过程中指挥一个智能体，本身就是一项独立的、可以学习的技能，而本仓库的构建过程，正是对这项技能一份诚实、完整的记录——不是一个假设性的例子。

## 需要说清楚的一个说法

"现在没人再手写代码了"这种说法夸大了——大量代码依然是手写的，而且在最要紧的地方永远都会是。但这个大方向是真实的，值得问一问它在这里究竟改变了什么。回头重读本课程的任何一课——第5集的 `resolve_within_root()`、第10集的 `eligible_indices()`、第13集统一的 `DATA_HEADER` 包装方式。它们的讲解要点没有一条是在解释*如何敲出一个 Python 函数*。每一条解释的都是*为什么*：为什么限制候选集比事后过滤更好，为什么剥除可疑文本会损坏那些恰好在讨论这类文本的合法内容，为什么证据关卡必须把一次*失败*的工具调用当作不算数的证据拒绝掉，而不只是要求"有过某次"工具调用。这一部分，不会因为由 AI 智能体来编写实现代码就凭空消失——这是你需要理解到足以*正确提出要求*的那一部分，也是当智能体的输出悄悄出错时，你需要能够识别出来的那一部分。架构素养和"会提示词"不是相互竞争的技能。前者正是让后者得以成立的基础。

## 讲解要点

1. **一次设定、贯穿整个构建过程的常设规则——这才是让一句两个词的提示词管用的原因。** "Continue to Episode N."（继续做第N集）——这几乎就是本课程绝大多数指令的全部内容，一字不差。这之所以行得通，是因为有那么几条规则，在很早的时候就被一次性确立下来，此后再也不需要重复：每一集都要同时交付代码*和*测试*和*一篇课程文档；课程文档里的每一处说法，在写下来之前都要对照真实输出验证过，绝不能凭空编造；没有那句明确的指令，就不会推进到第 N+1 集。一句简短的提示词，建立在一份明确、持久的约定之上，产出的是有纪律的结果。一句简短的提示词，如果背后没有这份约定，产出的就只会是智能体自己猜测你想要什么。
2. **一句提示词，对应一次专注、经过测试的改动——而不是"把整个东西建出来"。** 从来没有人要求过直接生成"这个智能体"。测试数量是一步一步、每一步都可验证地增长起来的：3 → 9 → 18 → 31 → 38 → 80 → 94 → 117 → 158 → 174 → 191 → 207 → 241 → 267 → 280 → 297 → 305，对应的真实提交次数，和新增能力的次数恰好一样多。一句范围限定在单一、可评审能力上的提示词，产出的是一份你在信任它之前真的能够从头到尾读完的 diff。"给我一套带访问控制和智能体循环的 RAG 流水线"这种提示词做不到这一点。
3. **每一次都要求验证——"相信我就行"这种回答，从智能体嘴里说出来和从一个人嘴里说出来一样，都不能接受。** 每一课的"现场演示"和"失败案例"部分，都是真实、被记录下来的输出，而不是描述"大概会发生什么"的文字。第9集的调用图，是在写下第一个测试*之前*，就针对 Loopline 的真实源码做过交互式核对的。第16集里 `localhost` 与 `127.0.0.1` 的发现——一次真实存在的、长达5秒的连接延迟——是实际测量出来的，不是凭空假设的。如果一个智能体关于自己输出的说法无法被重新运行、重新核对，那就应该把它当作未经验证的东西对待，因为它本来就是。
4. **要靠核对追踪记录来抓住过度自信，而不是只听叙述。** 这条原则可以递归地套用，第18集就抓到了一个真实的例子：现场模型自己的回答文本声称*"一次 query_graph 检查……显示"*——而那次请求真实的 `tools_called` 其实是 `["search_code"]`。可以核对的是追踪记录；文字只是一个说法。同一条纪律，往上再套一层，同样适用于叙述自己做了什么的 AI 编程智能体——读 diff，跑测试，不要把它的总结当成验证本身。
5. **用书面方式纠正偏差，而不是悄悄改写历史。** 当第8集改变了 `Document.citation` 的行为方式时，第1集的课程文档得到的是一段带日期的补记，而不是一次悄无声息的编辑。当第17集补上了第10集明确推迟处理的那个缺口时，第10集的课程文档得到的是同样的处理方式。一个能够悄悄修改自己此前说法、去迁就新现实的智能体，其历史记录就再也不值得信任了——正确的做法始终是一次看得见的更正，而不是一次看起来更干净的改写。
6. **在触碰陌生状态之前先调查清楚——智能体默认就应该抱有一个谨慎工程师会有的同等谨慎。** 课程进行到一半时，冒出来一个 `.gitmodules` 条目和一个 `video-production` 目录，和这里的任何工作都毫无关系。正确的做法是先去核实它究竟是什么(用户自己另外的一套工具)，然后才采取任何行动，此后本课程剩余部分的提交都改用限定路径范围(pathspec-scoped)的方式，这样它就不会被不小心卷入某个不相关的提交里。
7. **提示词本身不是安全边界——对一个编程智能体来说同样如此。** 本课程用第3、12、13集反复证明：一个 LLM 会同样爽快地执行一条坏指令和一条好指令，真正的安全来自校验、只读约定和测试，而不是来自好好地请求它。同一条性质，往上再套一层依然成立：一个被要求"想办法让它跑起来就行"的智能体，就会真的只做到这一点，包括抄一条本来会被一条谨慎提示词事先堵死的近路。*这次*构建真正的安全网，是第1条讲到的常设规则、每一份 diff 推送之前都有人真的去审查，以及一套必须始终保持全绿的真实测试套件。
8. **以上这些都不能取代另外18课的第1到第7条要点——恰恰相反，它依赖于那些要点。** 你没办法要求一个智能体去补上一个你自己都描述不出来的缺口。你也没办法认出一个你根本不知道是错的错误答案。"加上基于角色的访问控制"和"在排序之前而不是之后限制候选集，这样一次改写措辞就无法找回一份受限文档"，这是在向智能体提出两件非常不同的事情，而其中只有一个才是第10集真正做的事。架构知识不是本课程*绕开*来讲的那一部分——它恰恰是让提示词真正管用的那一部分。

## 练习

从本课程里任选三集，不去看它们实际是怎么构建出来的，写下你认为那条真实的指令必须要说明白哪些内容，才能产出那份精确的 diff、那个精确的测试数量、以及那篇精确的课程文档——不是"加上 RBAC"，而是真正被强制执行的那项特性，以及你要怎么判断它做对了。然后拿它和一句干巴巴的"加上访问控制"这种提示词大概率会产出的东西做对比。这两者之间的差距，才是这份文档真正想讲的那项技能。
